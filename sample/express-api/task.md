# タスク文

`bd create` に渡した文章そのもの、**ループに渡した指示はこれだけ**（動くベース・設定・土台のテストは人が用意 → [README.md](README.md) の中身の表）

```bash
bd create "メールアドレスを登録するエンドポイントを追加" -d "<下の仕様>"
```

タスクの題名は beads の上限が**500バイト**（日本語なら約160文字）、長い仕様は題名に入らないので `-d`（説明）へ書く、ハーネスは題名と説明の両方をワーカーへ渡す

## 仕様（`-d` に渡した文章）

```
src/register.js に メールアドレスを登録する Express ルーター registerRouter を実装し、tests/register.test.js で supertest を使って検証する。仕様: POST /register に JSON {email} を受け取る。形式チェックは正規表現1本で行い、型の事前チェックは書かない。形式不正なら 400 と {error} を返す、不正の全パターン（空文字・@が無い・@が2つ以上ある（例 a@b@c）・空白を含む・@の前が空・@の後が空）をテストで検証する。正しければメモリ上に保存して 201 と {email} を返す。登録済みのメールなら 409 と {error} を返し、409 の応答本文もテストで検証する。既存ファイル（src/app.js 等）は変更しない
```

## 書き方の理由

| 書いたこと | なぜ |
|---|---|
| どのファイルに 何を作るか（`src/register.js`・`tests/register.test.js`） | ハーネスが成果物として見るのは `src/` と `tests/` だけ（外を書き換えても元へ戻される） |
| 既存ファイルは変更しない | 既存ファイルの改変は 変異チェックがファイル単位で走るため通しにくい |
| 不正パターンを列挙 | 正規表現のアンカー（`^` `$`）を消す変異は、対応する入力がテストに無いと殺せない |
| 形式チェックは正規表現1本・型の事前チェックは書かない | テストが要求していない分岐を書かせない（検証されない枝は変異が生き残る） |

不正パターンの列挙を省いた最初の版は、正規表現のアンカーを消す変異を殺せず、2ラウンド×3回（計6回）書き直しても通らずに人への差し戻しになった
