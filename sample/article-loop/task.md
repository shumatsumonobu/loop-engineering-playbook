# タスク文

`bd create` に渡した文章そのもの、**ループに渡した指示はこれだけ**（土台の記事・設定・変異器は人が用意 → [README.md](README.md) の中身の表）

```bash
bd create "git worktree の使い方を説明する技術記事を書く" -d "<下の仕様>"
```

## 仕様（`-d` に渡した文章）

```
articles/worktree.md に git worktree の使い方を説明する技術記事を書き、tests/worktree.test.js で記事を検証する。記事に必ず含める要素: (1)「何が嬉しいか」「使い方」「片付け方」「注意点」という4つの見出し (2) bash のコードブロックで git worktree add と git worktree remove --force の2つのコマンド (3) 利点を箇条書きで2つ以上 (4) 公式ドキュメント https://git-scm.com/docs/git-worktree へのリンク。テストは上の要素を1つずつ「存在するか」で検証する、個数を数える検証（見出しが4つ以上など）は書かない。記事にはテストが検証していない文を書かない、同じ内容を2箇所に書かない。既存ファイル（articles/hello.md 等）は変更しない
```

## 書き方の理由

| 書いたこと | なぜ |
|---|---|
| どのファイルに 何を作るか（`articles/worktree.md`・`tests/worktree.test.js`） | ハーネスが成果物として見るのは `WORK_ROOT` と `tests/` だけ（外を書き換えても元へ戻される） |
| 含める要素を具体的に列挙 | 何を検証すべきかをテストに落とすため、曖昧だと検証されない部分が残って変異が生き残る |
| **個数を数える検証を書かない** | 「見出しが4つ以上」に対して記事に5つあると、1つ消しても条件を満たすので変異を殺せない（下） |
| テストが検証していない文を書かない・同じ内容を2箇所に書かない | 検証されない文と 重複した記述は そのまま生き残りになる（下） |

## 実験で分かったこと（$0 の事前検証）

タスク文を決める前に、スタブで変異器を回して確かめた

**個数を数える検証は変異を殺せない**

「見出しが4つ以上」「300文字以上」のような**下限**の検証は、記事に余裕がある分だけ変異が生き残る（1つ消しても条件を満たしたまま）

実測: 数を数える検証だけのテストでは 23個中 20個が生き残り、要素の存在で検証する形に変えたら 7個まで減った

**残った生き残りは「重複」と「検証していない飾りの文」**

- `## 使い方` を消しても、タイトル `# git worktree の使い方` が `/使い方/` にマッチして緑のまま＝重複
- 「作業コピーを追加する、新しいブランチを同時に作れる」＝どのテストも見ていない文

これは [proof/README.md](../../proof/README.md) の「冗長な実装が等価変異を生む」と同じ構造、記事では**重複した記述と装飾の文**がそれに当たる
