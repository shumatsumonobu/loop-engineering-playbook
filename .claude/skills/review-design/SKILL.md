# /review-design

設計書と規約は**実装を語る文章**、実装が変わると黙って嘘になる。レビューはその一致だけを見る

対象 ── `DESIGN.md`（設計の全部）／`CLAUDE.md`（開発の規約）／`.claude/rules/*.md`（書き方の基準）／`.claude/skills/*/SKILL.md`（レビューの手順）／`.claude/scripts/inspect.mjs`（検査が何を見ているか）

## なぜ要るか

**「〜しない」と設計で決めただけで、実際には〜できてしまう状態**が放置されていたことが実際にあった（[proof/README.md](../../../proof/README.md) の落とし穴25〜30）

- 「ワーカーに commit / close の**権限**を渡さない」── 権限では止まっていなかった（作業コピーの中で `git` も `bd` も叩ける）
- 「破壊的な git 操作は**必ず作業領域に限定**」── `reset --mixed`・`checkout -B`・`reset --hard` が実装に3箇所あった
- 「チェック一式（**ビルド＋テスト＋型**）」── ハーネスが呼ぶのは `npm test` だけ

## 先に読む

- `README.md`（同じ断定が両方にあることが多い）
- `harness/integrated.mjs`（断定を突き合わせる相手）
- 直した規約が防ぐはずの失敗が `proof/README.md` の落とし穴にあるか

## やり方 ── 断定を列挙して実装と照合する

**観点は [doc-review-passes.md](../../rules/doc-review-passes.md) の A〜C を全部 通す**（見る観点を減らさない）、直す時の手順は同じファイルの `## 直す時`、下は設計書で特に効くものの詳細

視点を渡して読ませても出ない（実測: 視点を渡した回は**0件**、断定を1行ずつ突き合わせた回は連続で発見）

### 1. 断定を列挙する

まず**強い断定**を全部 開く（1件ずつ実装を確かめられる量に収まる）

```bash
cd /path/to/loop-engineering-playbook
grep -nE "権限|必ず|できない" \
  CLAUDE.md DESIGN.md .claude/rules/*.md .claude/skills/*/SKILL.md .claude/scripts/inspect.mjs
```

**`だけ`・`しない` は一般語なので桁がちがう**（「1行だけ」「変更しない」など断定でない用法が大半）、全部は開けないので**直した所の周辺だけ**見る ── 下の表の「〜だけを見る」「既定は〜」「N回で〜」はここで拾う

```bash
cd /path/to/loop-engineering-playbook   # git diff はルートからの相対パスを返すので、ここで打たないと空振りする
git diff --name-only <直す前のコミット> | grep '\.md$' | xargs grep -nE "だけ|しない"
```

### 2. 1件ずつ実装を開いて確かめる

**推測で判定しない**、`harness/integrated.mjs` の該当箇所を読む

| 断定の型 | 確かめ方 |
|---|---|
| 「ワーカーは〜できない」 | **できてしまう前提で**、ハーネスが検出して戻しているかを見る（権限では止まらない） |
| 「〜だけを見る / 実行する」 | 実際に呼んでいるコマンドを数える（`run(` / `spawn(` を grep） |
| 「〜に限定している」 | 引数を確かめる（`-- src tests` のようなパス限定が本当にあるか） |
| 「既定は〜」 | `process.env.X || "既定"` の右辺と一致するか |
| 「N回で〜」 | `MAX_ATTEMPTS`・`MAX_ROUNDS`・`T` の値と一致するか |

### 3. 用語が1つに揃っているか

同じものを2つの語で呼んでいないか、初出で定義しているか

**全部 読まずに、数えて並べる** ── 件数が多すぎて通読できないので、割れているものだけを浮かせる

```bash
cd /path/to/loop-engineering-playbook
grep -rohE "[0-9]+[つ枚個]のゲート|ハーネス|ワーカー|作業コピー|worktree" \
  CLAUDE.md DESIGN.md .claude/rules/ .claude/skills/ | sort | uniq -c | sort -rn
```

数が少ない方が割れの候補、**ただし規約の「実際に起きた」が引用した過去の割れも拾う**ので実物を開いて確かめる

**実際に起きた**: 「機械」が定義されないまま主語として72箇所あり、しかも**3つの別物**（合否を出すもの／手順を進めるもの／人が判断しないという性質）を指していた

### 4. 規約どうしの穴

**同じことを言っている規約が複数あるとき、そのどれからも漏れる場合がある**

実際に起きた ── 「他のファイルの手順番号を指さない」と「先の手順への参照を書かない」の2つがあったのに、**「同じファイルの中で前の手順を指す」が両方からすり抜けていた**

規約を足す時は「**この規約はどの失敗を防ぐか**」を1件 書く、防げない失敗が残っていないか確かめる

## 出し方

**見つからなければ0件で返す** ── 数を埋めるために弱い指摘を足さない、根拠（ファイルと行）を書けないものは推測なので出さない

| 重大度 | 判定 |
|---|---|
| 高 | **読者や次の開発者が間違った行動をする**（実物と食い違う断定・数字の矛盾・画面と文書の食い違い） |
| 中 | **読み進めるのに引っかかる**（曖昧・前方参照・用語の割れ・未定義） |
| 低 | 表現の弱さ・重複 |

各件に **現在 / 実物ではどうか / 案 / 根拠（ファイルと行）** を付ける

## 終わったら

- `node .claude/scripts/inspect.mjs` が exit 0
- ハーネスを触ったなら [MAINTAINING.md](../../../MAINTAINING.md) の回帰も回す
