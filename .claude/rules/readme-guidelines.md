# README の基準（書く時・レビューする時）

README.md が果たすのは **初見の読者が 仕組みを理解し、自分に使えるか判断し、自分のプロジェクトへ入れられる**こと

文体・用語・事実の裏付けは [doc-guidelines.md](doc-guidelines.md)（同時に読み込まれる）、ここはそれを果たせているかだけ

下は**同時にできない読み方**（全体を見ながら1手順ずつ精読はできない、精読しながらコマンドは打てない）、順に通す

読み終わってから直すのではなく、**1つ通すごとに直して次へ進む**

## 俯瞰 ── 節の並びを見る

**ここは節の名前も並びも指定しない** ── 構造は改善し続けるものなので、規約で今の形を固定すると次の改善がガードされる、見るのは**役割の分かれ方と、読者が困る順序**だけ

### 読者向けと 自分たちの実証を、別の大きい節に分ける

**読者向けの節に入れていいのは、読者が自分のプロジェクトでやることだけ** ── リポジトリ外の検証用リポジトリ・スタブ・自動登録されるデモ・実測の画面といった**こちらが検証のためにやった話は入れない**、実証の側へ出す

- **判定は但し書きが要るかで決まる** ── 「これはスタブで回したもの」「これは検証用の環境で」と断らないと嘘になるなら、その節に置くべき内容ではない
- 実際に起きた: 読者が試すデモが「検証」の節の中に埋まっていた
- 実際に起きた: スタブでリポジトリ外の検証用リポジトリを回した画面を実行の手順に貼り、**「検証用の空のリポジトリで回したので…」という但し書きまで足した**（但し書きを書いた時点で気づけたはず）
- 実測の数字は例外 ── **主張に1つ添える裏付け**（「TypeScript でも通る・$0.90」）は読者の判断材料なので読者向けの節に置いてよい、持ち込まないのは**実験の場面そのもの**

### 読者が困る順序になっていないか

- **冒頭で「読者が何を得るか」が分かるか**
  - 実際に起きた: 用語の定義 → ツール6つの表 → ディレクトリ構成 で始まり、「このリポジトリを使うと何ができるのか」がどこにも無かった
  - 先に「何が手に入るか」、次に「何を解決するか」
- **読者が「自分に使えるか」を判断する材料が、作業手順より前にあるか**
  - 実際に起きた: 用途ごとの判断表がセットアップの手順の後ろにあり、使えないと分かる前に手順を踏ませていた
- **対象外の読者が、手順に入る前に対象外だと分かるか**（言語・ツール・構成の要件）
  - 実際に起きた: 導入先が JavaScript/Vitest/ESM 前提であることがどこにも書かれておらず、Python のプロジェクトを持つ読者は**依存を入れる手順まで進んで初めて**気づく作りだった
  - 「何がインストール済みであること」は**実行する側**の話、**導入先の要件**は別に書く
- **軽い入口（試す・デモの類）を置くなら、重い手順より前に**
  - 実際に起きた: リポジトリ外の検証用リポジトリで1周試せる節が、セットアップの手順より後ろにあった
  - 置く/置かないは構造の判断なのでここでは決めない、**置くなら位置だけ守る**
- **参照情報（ツールの一覧・ディレクトリ構成など、読んで使うのではなく引く情報）が冒頭を占めていないか**
  - 導入を決めた後に要る情報なので、冒頭ではなく該当する節の近くへ置く

## 逐条 ── 手順を1つずつ見る

- **コマンドを打つ場所が常に明示されているか**（`cd` が実コマンドとして書かれているか）
  - 実際に起きた: 括弧書きで「ここから自分のリポジトリ」と書くだけで `cd` が無く、読者はハーネスのフォルダのまま `npm install` を打つ導線になっていた
  - 作業場所が複数あるなら、**冒頭で場所を定義**して切り替わる手順にだけ印を付ける（例:「作業する場所は2つ ── ハーネスと導入先」＋ `［導入先］`）
- **手順の前提が、その手順より前に書かれているか**
  - 実際に起きた: 手順の一部を前の節へ動かしたのに、前提（Node.js・git）は元の節に置いたままだった ── **節を動かしたら前提が置き去りになっていないか毎回 見る**
- **「手順N」への参照が無いか**（節をまたいでも、手順の中どうしでも）
  - 節を動かすと壊れる、それ以前に**読者がその手順まで戻らないと意味が取れない**
  - 番号をやめて**その場で何のことか分かる書き方**にする ── `手順3 の bd init が追記した` → `bd init が追記した`
  - 番号の横に何をする手順か書いてある表だけ可（`inspect.mjs` が指している箇所を毎回 出す）
- **1手順＝1作業になっているか**
  - 1つのリスト要素に複数の作業や注意事項を詰め込まない
- **その手順の実行に要らない情報が混ざっていないか**（読者はそこで一度手を止める）
  - **後でやることの予告** ── 実際に起きた: 手順3 に「この後 CLAUDE.md への追記がある」と書いていた、そこで要らない情報は読者の手を止める
  - 読者が触らない内部動作 ── 実際に起きた: 設定をコピーするだけの手順に「結果は `reports/mutation.json` に出てハーネスがそれを読む」と書いていた
  - 自分たちの実証記録への誘導 ── 実際に起きた: 規約を貼り付ける手順の途中で proof へ飛ばしていた、信頼性の担保は実証の側の仕事
  - **その手順では起こらない状況** ── 実際に起きた: タスクを登録させた後の実行手順に「タスクが0件ならデモタスクが登録される」と書いていた（自分でタスクを登録した読者には起こらない）
- **確認方法が書かれているか**
  - 間違えても黙って進んでしまう手順には「確認: 〜」を付ける（付けすぎない、実際に黙って進む所だけ）

## 事実照合 ── 実物と突き合わせる

- **書いたコマンドを実際に実行して通したか**
  - 実際に起きた: `MUTATOR=../my-articles/mutate-md.mjs` と相対パスで書いたが、検証したのは絶対パスだった（後から $0 で実証して正しいと確認）
- **手順どおりに操作すると本当にそうなるか**（ハーネスのコードと突き合わせる）
  - 実際に起きた: 「変異対象が違う場合は `mutate` を書き換え」と書いたが、ハーネスが実行時に `--mutate` で上書きするので**書き換えても効かない**、読者に不要な作業をさせたうえ「直したのに効かない」と混乱させる

## 仕上げ ── 初見の読者役に踏ませる

手順を大きく変えた時は実際に踏ませて確かめる（$1〜2）

**小さい既存プロジェクト**を用意して（動くコードが1つ・テストは無し・git 初期化済み）、README だけを情報源にした `claude -p` を走らせる

空のプロジェクトでは駄目、既存コードにテストを足す手順が成立しない

プロンプトに必ず入れること（これが無いと穴が見つからない）

- **README に書いてあることだけを根拠に進める**、書いていない手順や値を自分の知識で補わない
- **決められない時はそこで止めて報告する**、推測で進めない
- ハーネスのリポジトリは書き換えない、変更は導入先の中だけ

報告させること: どこまで進めたか / **詰まった箇所と README の何が分からなかったか（該当行を引用）** / README に無くて自分で判断したこと / 迷わず進めた箇所

実測: この方法で「テストを最低1本と言われても何に対して書くか分からない」「Git Bash での `BASE` の書き方が無い」の2件が見つかった
