# ドキュメント共通の基準（書く時・レビューする時）

書き終えたら **`node .claude/scripts/inspect.mjs`** を回す（何を見るかは実行すると項目ごとに出る）、中身の正しさはこの基準で人が見る

対象は**このリポジトリで保守するドキュメント**（上の `paths` に書いたもの）

`sample/*/src/`・`sample/*/tests/`・`sample/*/articles/` の中身は**保守しない**（ループの生成物＝実証の証拠なので編集も規約の適用もしない）

「実際に起きた」が付いた項目は**このリポジトリで実際に見つかった不具合**、付いていない項目は過去の指摘から一般化したもの

対象ごとの基準は別ファイルにある、対象を読むと同時に読み込まれる

- [readme-guidelines.md](readme-guidelines.md) ── README.md（導入手順書としての品質）
- [sample-readme-guidelines.md](sample-readme-guidelines.md) ── sample の README.md と task.md（実際に回した記録としての品質）

## 文体

- **行末**に句点（。）を付けない、体言止めにするか 読点でつないで短く終える
  - **文中で文を区切る句点は残す**、2つの文を読点でつなぐと悪文になる
  - 実際に起きた: 「網羅性は無い**。**だから『生き残り0』の意味は…」の句点を読点に置き換えて、意味の切れ目を消した（「句点を使わない」を全廃と読み違えたのが原因、消すのは行末の1個だけ）
  - 確認は `grep -n "。" <file>` で**全部の句点を列挙して1件ずつ見る**、`grep -nE "。\s*$"` のような行末だけの検査は 表のセル末尾（`… 。|`）や 括弧閉じ（`…。）`）を取りこぼす
  - 判定: 文中で文を区切っているなら残す、行の最後・セルの最後・括弧の直前で文が終わっているなら消す、引用したタスク文など原文のまま載せる箇所は例外
- 内輪の略語・比喩を読者向け文書に出さない（リポ→リポジトリ、棚→タスク、park→人に差し戻し）
  - 実際に起きた: 読者向け README のリンク文言に「落とし穴」を使っていた、読者にはそれが何を指すか分からない
- **書き手の頭にある専門用語をそのまま出さない**、読者が**何を書けばいいか**の言葉に翻訳する
  - 契約 → **返す値の形** ／ インターフェース → **関数の書き方** ／ スキーマ → **項目の並び** ／ ペイロード → **渡す中身**
  - 実際に起きた: 他の言語で変異チェックを自作する手順を「変異器の契約」と書いた、読者は「何を守れば動くのか」が分からない（コードのコメントに書いた語を、そのまま読者向けへ持ち出したのが原因）
  - 判定: **その語を消しても手順が書けるなら消す**、消せないなら初出で1行 定義する
  - 確認: 節を書き終えたら**その節で初めて出した語を全部 列挙**し、1つずつ「この文書のどこで定義したか」を答える、答えられない語は残さない
- **評価を記号で表さない**、言葉で書く（あり／無し／間接的）
- **絵文字を使わない**、指し先も言葉で書く
  - 実際に起きた: 本文が「表の `🟡` はこっち」と書いていたが、**その表に `🟡` は無かった**（参照が空振り）、記号で指すと消えても気づけない
- 用語は初出で定義する
  - 実際に起きた: `ハーネス` は本文に20回出るのに、定義はツール表のセル内だけだった（表は読み飛ばされる）、`緑/赤`・`生き残り` は未定義のまま多用していた
- 前方参照しない（説明より前にその用語を使わない）
  - 実際に起きた: 冒頭で「人への差し戻し」を使ったが、説明は後ろの節にあった
- 同じ修飾語を繰り返さない
  - 実際に起きた: 「自分の」が12箇所、**場所を冒頭で1度 定義すれば各手順で繰り返す必要は無い**（例:「作業する場所は2つ ── ハーネスと導入先」と宣言して、切り替わる箇所にだけ印を付ける）
- メタ言及・自己正当化・読者への判断の押し付けを書かない

## 構成

- 同じ内容を2箇所で説明しない、するなら対応が見えるようにする
  - 実際に起きた: mermaid 図と3つのゲートの表が同じ内容を説明していたが、図にゲート名が無く対応が読み取れなかった
- 表の1セルを長文にしない（GitHub の表は横に潰れる）
  - 実際に起きた: 3列目に80字超の説明を入れて読めなくなった、見出し＋段落に開くと直る
- 一覧表に存在しないファイルを載せない
  - 実際に起きた: 中身の表に「CLAUDE.md ── **無し**」という行があった、表から出して注記にする
- **間違いを1件 直したら、同じ言い回しが他に無いか全文を数える**（「ここだけ直した」は「他は間違ったまま」と同じ）
  - 実際に起きた: 「ワーカーに commit の権限は無い」を README で直したが、DESIGN に同じ言い方が3箇所 残っていた（proof の落とし穴30）
- **同じものを2つの言葉で呼ばない**（用語を足した時は既存の文書を全部 grep する）
  - 実際に起きた: README が「3つのゲート」、DESIGN・proof・CHANGELOG・ハーネスのコメントが「3枚のゲート」で17箇所ぶん割れていた、1つの sample の README では同じファイルの中で混在していた
- 現象の説明で終わらせず「で、どうすればいいか」まで書く

## 事実の裏付け（実物と突き合わせる）

- **書いた主張に実測の裏付けがあるか**
  - 実際に起きた: 「製品アイデアのリサーチや 作る/作らないの判定にも使える」と書いたが、その2つは一度も実走していなかった
  - 実証していない主張は書かない、**削るだけで終わらせず 読者が次に何をすればいいかへ着地させる**（判断表・実例へのリンク）
- **数字が実物と一致するか**
  - 実際に起きた: 「落とし穴15件」（実際は18件）、「テスト12本が緑」（記事を検証しているのは10本、残り2本は土台のテスト）
- **前提として書く実行環境の版は、固定した依存の `engines` から取る**（自分が動かした版でも、なんとなくの下限でもない）
  - 実際に起きた: 前提を「Node.js 18 以上」と4箇所に書いていたが、固定している Vitest 4.1.10 の `engines` は `^20 || ^22 || >=24`、Stryker 9.6.1 は `>=20`、**Node 18 の読者は依存が入らず手順3で詰まる**（実走は全部 Node 24 だったので誰も踏んでいなかった）
  - 確認は実物から ── 版を固定しているのは sample、ルートの `package.json` は依存を持たない

    ```bash
    cd /path/to/loop-engineering-playbook
    node -e "const l=require('./sample/express-api/package-lock.json'); for(const [k,v] of Object.entries(l.packages||{})) if(v.engines && /^node_modules\/(vitest|@stryker-mutator\/core)$/.test(k)) console.log(k, v.version, JSON.stringify(v.engines))"
    ```
- **「N個とも」「全部」と数えて書く時は、数える対象の定義を先に決める**
  - 実際に起きた: 「要件を5つとも外したプロジェクトで通った」と書いたが、要件表5行のうち外れていたのは3行（言語は満たしていた）、読者が「要件は全部無視できる」と誤解する
- **他のファイルを数で指さない**（手順番号・`N種類`・`N通り`・`N行`）── 参照先が1つ増減すると**黙って腐る**、数の代わりに**何が変わるかを並べた表**を置く
  - 判定: **その数を消しても読者が同じ行動を取れるなら消す**、消せないなら実物で数え直してから書く
  - 手順番号は**番号の横に何をする手順か書いてある時だけ可**（例 `| 3 依存を追加 | …`）
  - **他のファイルの手順を指したい時は節へのリンクにする**（`](../../README.md#セットアップ)`）── 節は番号と違って手順を足しても動かない
  - **同じファイルの中でも番号だけで指さない** ── 読者はその手順まで戻らないと意味が取れない、**その場で何のことか分かる書き方**にする（`手順3 で生まれた package-lock.json` → `npm install で生まれた package-lock.json`）
  - 例外は実験の記録（`proof/`）── 当時どの手順で詰まったかは事実なので番号のまま残す、ただし今の手順と一致するかは確認する
  - 実際に起きた: sample が「13手順のうち5つが変わる（残り8つ）」と書いていて、本体の手順を1つ直すたびに3つの数が同時に嘘になる形だった
  - 実際に起きた: 「Python の変異器は7種類」が実物8種類だった（`not` を消す変異を後から足した時、コードの表だけ直して数を直し忘れた）
  - 実際に起きた: README の手順の中に「手順3 で〜」が5箇所あり、上から実行している読者が毎回 前へ戻る必要があった
- **実測の数字は記録（`proof/README.md`・各 sample の README）が持つ、一覧や索引の文書には書かない**
  - 実際に起きた: `sample/README.md` の一覧表に3題材ぶんの実測値があり、各 sample の README と二重だった＝1回 走らせ直すたびに両方 直すことになる
  - 例外は**読者が判断に使う数字**（本体 README のコストと時間）── これは残す、代わりに出典（`proof/README.md`）を明記する
- **別のドキュメントと矛盾していないか**
  - 実際に起きた: Stryker の対応範囲（README「JavaScript/TypeScript・C#・Scala」 vs sample「JavaScript しか壊せない」）、DESIGN の「変異ルールを自作しない」 vs sample で自作したこと
  - 1つの事実は1箇所だけに書き、他はリンクで参照する（SoT は CLAUDE.md の表）
