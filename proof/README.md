# proof — 土台とゲートを実証したハーネス（積み上げの記録）

**設計の SoT は [DESIGN.md](../DESIGN.md)、ここはその「実証コード」**（step0〜3 で実際に動かしたもの）
使い捨ての sandbox で回したので、**このリポジトリにあるのは記録＋実装の種**、そのままでは動かない（下の再現手順が要る）

**※ 完成版の `integrated.mjs`／`stryker.config.json` は本体として [`../harness/`](../harness/) に昇格済み、ここ（proof/）に残るのは 積み上げの各段階（`harness.mjs`→`harness7.mjs` ほか）と実測の記録**

**コード内のコメントも当時のまま**、今の実装や用語とは違う ── 例えば `harness.mjs` の「ワーカーに commit / close の権限なし」は後から誤りと判明している（[落とし穴30](#実証で判明した落とし穴設計に無かった)・実際には叩けるのでハーネスが検出して取り消す）、現在の仕組みの説明は [../README.md](../README.md)

### それぞれが証明したこと

**`harness.mjs`**（step0）

- **AI の自己申告では1行も保存されない**
- 嘘つきワーカー（何もせず「終わった」と申告）は、ハーネスが実テストで赤を見て**保存を拒否・claim を解放・人に差し戻し**
- 本物のワーカーは緑になって commit と `bd close` まで進んだ

**`harness2.mjs`**（step1）

- **claim の排他**（実レースで片方が弾かれ、別のタスクを取った）
- **作業コピーの完全な隔離**（互いのファイルを持たない）
- 各ワーカーが独立にゲートを通る

**`harness3.mjs`**（step2）

- **依存** ── A が close されるまで B は ready に出ない、close の瞬間に解放されて即 claim される
- **外側ループ** ── 取る → やる → ゲート → 完了 → 次の1件、タスクリストが空になったらワーカーが自分で終了する

**`integrate.mjs`**（統合）

- worker の枝を**1本ずつ main へ統合 → 毎回 全テストを再実行 → 緑なら採用・赤なら巻き戻す**
- **「統合できたこと」と「統合してよいこと」は別**

**`harness4.mjs`**（step3・難所）

- **テストの質もゲートで判定する**、通す順序は次のとおり
    1. テストだけ書かせる
    2. **赤先行** ── 実装が無い状態で走らせ、通ったら不合格（何も検証していない弱いテスト）
    3. **凍結** ── この時点の `tests/` の内容を記録しておく
    4. 実装させる
    5. 記録した内容から書き換えられていたら不合格（弱めて通すズル）
    6. 緑で保存
- **手抜きワーカー（`expect(true).toBe(true)`）をゲートが弾き、本物のテスト（8ケース）は通した**

**`harness5.mjs`**（step3-b・変異チェックの自作版）

- harness4 に**変異チェック**を足した ── 緑になった後、実装をわざと壊して（`*` を `+` へ、`<=` を `<` へ など）テストが赤くなるかを確かめる
- **緑のまま＝その壊し方をテストが検出できない＝テストが弱い＝不合格**、この「壊してもテストが緑だった箇所」を以降 **生き残り**と呼ぶ
- **型だけ見るゆるいテストは赤先行を通過してしまった**が、変異チェックが生き残り3個を検出して弾いた
- **ただし自作の変異ルールは弱い**（落とし穴8）ので harness6 で捨てた

**`harness6.mjs` ＋ `stryker.config.json`**（step3-c・Stryker 本採用）

- 変異ルールの自作をやめ、**実在のツール Stryker** に置き換えた（同じ実装から、自作は変異1個・**Stryker は7個**）
- **ゲートは「変異スコアが閾値以上」ではなく「生き残った変異が0個」**（落とし穴10）
- **手抜きワーカーを弾いた**（`npm test` は緑なのに生き残り 2/3）

**`harness7.mjs`**（step3-d・フィードバックと人への差し戻し）

- ゲート3で落ちた時、**生き残った変異を次のワーカーに渡して書き直させる**（「`if (a===0\|\|b===0)` を `if (false)` に壊してもテストが全部 緑だった＝ここを検証しているテストが無い」）
- **3回 失敗で人に差し戻し＝無限に書き直させない**
- **実機で人への差し戻しまで到達し、人が見たら原因は実装の冗長さだった**（落とし穴11）

**`selfcheck.mjs`**（step3-e・変異ゲートの自己チェック）

- ゲート3を信じる前の検算、**Stryker の生き残りを素の `npm test` と突き合わせる**
    - `npm test` が赤 ── テストは殺せている＝**Stryker が嘘＝ツールが壊れて出した偽の生き残り**、ゲートを使わず人に差し戻す
    - `npm test` も緑 ── **本物の生き残り**
- **壊れはファイル単位**なので、変更した成果物ごとに検算する
- **実コードで実証** ── `routes.js`（CommonJS と HTTP 経由の統合テスト）は8個とも偽で「壊れ」を検出、`index.js`（ESM）は6個とも本物と正しく判定（落とし穴12）

**`integrated.mjs` ＋ `stub-worker.mjs`**（統合・通し）

- 別々だった土台（harness1〜3）とゲート（harness4〜7）と自己チェックを**1本に統合した**
- **肝は移植** ── ゲート一式を `spawnSync` から async へ移して並列の骨格に載せた（`spawnSync` はイベントループを止めるので並列にできない）
- **`claude` を実際に呼んだ** ── 1本（gcd・$0.62）、並列2本（gcd と isPrime・$1.16・claim の排他が実レースで効いた）
- 不合格 → フィードバック → 回復、3回で人に差し戻し、は **`stub-worker.mjs`**（わざと弱いテストを書く決定論的なスタブ）で実証した（自己チェックが発火・誤った差し戻しなし・無限ループなし）
- **実バグを1件 見つけて直した**（落とし穴13・`--add-label`）、コストの実測は下の専用の節

**`stub-worker-md.mjs`**（コード以外の成果物・記事）

- 記事ループ用のスタブ、`WORK_ROOT=articles` と自作の変異器（[../sample/article-loop/mutate-md.mjs](../sample/article-loop/mutate-md.mjs)）を差し替えた通しを **$0 で検証**
- 弱いテスト（23個 全部 生き残る）→ フィードバック → 強いテスト（7個まで減る）→ 人に差し戻し、を決定論的に再現した
- **合格までは行かない** ── 強いテストは固定なので必ず7個 残る、その7個は「記述の重複」と「どのテストも見ていない飾りの文」で、落とし穴18 そのもの
- **課金する実走の前に、ここでタスク文の書き方（個数を数える検証は変異を殺せない）を確定させた**（落とし穴18）

**`stub-worker-attack.mjs`**（迂回の再検証）

- わるいワーカー（`ATTACK=commit / disable / tamper / config / testcmd / close`）を決定論的に再現し、落とし穴25〜29 で塞いだ防御が今も効くかを $0 で確かめる
- 回し方と判定は下の専用の節と [stub-worker-attack.mjs](stub-worker-attack.mjs) の冒頭

**`stub-worker-parallel.mjs`**（並列でしか出ない壊れ方）

- w1 をテストの段階で10秒 待たせ、その間に w2 が1タスクを完了させる＝「自分の呼び出し中に他のワーカーがタスクを閉じた」状況を決定論的に作る
- 落とし穴31 の再現と、修正の確認に使う

**`integrated-real.mjs`**（本物リポジトリ）

- 実保守タスク用の単発ランナー、`integrated.mjs` と違い**並列と作業コピーと統合を載せない**
- 適応したのは3点だけ ── 変異を変更した行だけにスコープする、プロンプトを既存コードの修正用にする、`BASE` で直接 回す（対象パスは当時のまま）

## 設計の核（コードで読むならここ）

- **ワーカーは「手」、ハーネスが唯一の「門番」** ── ワーカーは作業コピーの中で `git commit` も `bd close` も**叩けてしまう**（権限では止まらない）、ハーネスが呼び出しの前後で検出して取り消す・開け直す（下の落とし穴25・29）
- ハーネスが**自分で `npm test` を走らせ**、**exit code が 0（緑）の時だけ** commit＋close
- 赤なら書き直し、打ち切りで人の対応待ち＝claim 解放（**この proof のコードは3回**・[harness7.mjs](harness7.mjs) の `MAX_ATTEMPTS = 3`／現行の [harness/integrated.mjs](../harness/integrated.mjs) は3回×2ラウンド）

1. **同じ名前の2ワーカーは両方 claim に成功する**

    - **原因** ── `bd update --claim` は「自分が claim 済みなら冪等」なので、名前が同じだと排他が効かない
    - **修正** ── `BEADS_ACTOR=w1 / w2` を環境変数で分ける、別の名前なら他人の claim 済みは `exit 1` で弾かれる

2. **ベース（main）は常に緑に保つ**

    - **何が起きるか** ── 未着手タスクの受け入れテストを main に先置きすると、各作業コピーに他タスクの赤いテストが入り、全ワーカーのゲートが道連れで永久に赤になる
    - **設計** ── 各タスクの受け入れテストは、そのワーカーが自分の作業コピーで書く

3. **依存が直列だと、ワーカーを増やしても1本しか動かない**

    - 並列が効くのは独立したタスクが複数ある時だけ

4. **`bd` は npm の `.cmd` シムなので Node から shell 経由で呼ぶ**

    - `shell:true` は引数を自動クォートしないので、日本語と空白は自前でクォートする

5. **成否は exit code で判定する、パイプ越しの `$?` は嘘をつく**

    - パイプの `$?` は最後のコマンドの終了コードになる

6. **`git clean -fd` をリポジトリ全体に打ったら、未追跡だったハーネス自身が消えた**

    - **修正** ── `git clean -fd -- src tests` のように作業領域だけを掃除する
    - この時ハーネスはこのリポジトリに保存済みだったので復元できた、実証コードをリポジトリに置く価値が事故で証明された

7. **テストの凍結が無いと、赤先行チェックは無意味になる**

    - 実装の段階でワーカーがテストを弱められるなら、赤先行はすり抜けられる
    - 赤先行と凍結はセットで初めて意味を持つ

8. **変異チェックの変異ルールを自作してはいけない**（`harness5.mjs` の `MUTATIONS` が実証用の最小版）

    - **何が起きるか** ── 自作ルールは空白区切りの演算子しか壊せない

        ```js
        for (let i = 2; i <= n; i++) { result *= i; }   // " <= " しか一致しない
        ```

        この実装では `*=`・`++`・数値リテラルを見逃し、変異を1個しか試せなかった（＝ゲートが浅い）
    - **修正** ── 実在の変異テストツールを使う（JavaScript / TypeScript は Stryker、Java は PIT、Python は mutmut、Rust は cargo-mutants）
    - **この時点の判断は誤りだった** ── ゲート条件を「変異スコアが閾値以上（例80%）」にするつもりだったが、次の落とし穴10 で撤回した、正しくは「生き残った変異が0個」

9. **変異チェックの後は必ず実装を元に戻す**

    - 戻し忘れると壊れたコードをコミットしてしまう
    - Stryker に任せれば自分で戻す必要は無い、これも自作をやめる理由

10. **変異スコアの閾値をゲートにしてはいけない**

    - **実測**

        | 実装 | テスト | 変異スコア | 生き残り | 「スコア>=80%」 | **「生き残り0」** |
        |---|---|---|---|---|---|
        | factorial（ループ） | 本物 | 100% | 0 | 合格 | 合格 |
        | factorial（ループ） | ゆるい | 28.57% | 5 | 不合格 | 不合格 |
        | **gcd（whileループ）** | **ゆるい** | **80.00%** | **1** | **すり抜けた** | **不合格** |
        | gcd（再帰） | 本物 | 100% | 0 | 合格 | 合格 |
        | gcd（再帰） | ゆるい | 60.00% | 2 | 不合格 | 不合格 |

    - **原因** ── `while (b)` を `while (false)` に壊すと無限ループになり、変異テストはタイムアウトを「検出した」と数える
    - つまり**何も検証していないテストが、実装がループを持っているというだけで点をもらう**、実際にゆるいテストがスコア80%でゲートを通過してコミットされた
    - **修正** ── ゲートは「生き残った変異が0個」にする、「テストが検出できない壊し方が在る」＝まさに知りたいことそのものなので、実装の形で揺れない

11. **「等価変異で詰まった」の正体は、たいてい実装の冗長さ**

    - **実機で人への差し戻しまで行った例**

        ```js
        if (a === 0 || b === 0) return 0;    // 要らない（下の式が、片方が0なら勝手に0を返す）
        return (a * b) / gcd(a, b);
        ```

        このガードは冗長なので、`||` を `&&` に壊しても全パターンで結果が同じ＝誰にも殺せない変異になる
    - **経過** ── ワーカーが3回テストを書き直しても通らず人に差し戻し、人が見たら問題はテストではなく実装だった、ガードを消したら変異6個が全部 検出されて合格（タイムアウトも0になった）
    - **教訓その1** ── 人への差し戻しは「面倒な例外処理」ではなく、実装の設計ミスを見つける出口
    - **教訓その2** ── AI に「等価変異だから無視していい」と判断させてはいけない、「殺せない＝等価です」と言えばどんな弱いテストも通せる＝自分の答案を自分で採点することに逆戻りする、無視の印（`// Stryker disable`）を付けられるのは人間だけ

12. **変異ゲートには自己チェックが要る**（実コードで回して分かった・この節で一番 大きい）

    - **何が起きたか** ── おもちゃ（純粋関数）ではなく当時 手元にあった Express API（135行・26テスト・このリポジトリには入っていない）に Stryker を素で当てた

        ```
        変異 138個 / スコア 7.25% / routes.js は killed 0（116個 全部 生き残り）
        ```

        「生き残り0」ゲートなら全タスク即 不合格 → 永久に人への差し戻し に見えた
    - **断定せず検証したら逆だった** ── 生き残ったと報告された変異（`validateTitle` の条件を `true` に固定）を手で入れたらテストが4本 赤くなった、つまりテストは強く、ツールが変異を効かせられていなかっただけ
    - **原因** ── テストが supertest で HTTP 経由に叩き、ソースを直接 import していない、さらに `routes.js` が CommonJS だったため、ツールが「変異したファイルに関連するテスト」を辿れず「関連テスト0件」→ 全部 生き残りと報告した（Stryker 自身が `Vitest failed to find test files related to mutated files` と出した）、ESM で直接 import している `index.js` は正常に検出できていた
    - **怖いのはエラーで止まらないこと** ── それっぽい低スコアを出すので、信じると完璧なテストでも全部 不合格になり人への差し戻しの嵐になる
    - **修正** ── ゲートを信じる前に検算する（`selfcheck.mjs`）、Stryker の生き残りを1個ずつ手で当てて素の `npm test` を回す、赤ならテストは殺せている＝ツールが壊れて出した偽の生き残りなのでゲートを使わず人に差し戻し、緑なら本物の生き残り
    - **壊れはファイル単位** ── 同じリポジトリでも `index.js`（ESM）は正常、`routes.js`（CommonJS）は壊れ、だから変更した成果物のファイルごとに検算する（全体で上限を切ると、正常なファイルが先に回って壊れたファイルに届かず見逃す、実際にこのバグを踏んだ）
    - **実証** ── `routes.js` の生き残り8個は全部 ツールの壊れによる偽の報告と検出、`index.js` の生き残り6個は全部 本物の生き残りと正しく判定、つまり常に警告するのではなく壊れている時だけ警告する
    - **教訓** ── 生の変異スコアを鵜呑みにしない、おもちゃで100点でも実コードで正しく動くとは限らない（モジュール形式・テストの書き方・ツールの噛み合わせが全部 効く）

    - **教訓** ── ゲートの監視範囲を「今回 触った物」に絞ると、触っていない物が抜け道になる、守る対象は「この走の成果物」ではなく「合否を決める判定材料の全部」

**落とし穴25〜27 は同じ1つの原因から出た** ── 「ワーカーは〜しない」と設計で決めただけで、実際に〜できてしまう状態を放置していた

28. **ワーカーは作業領域の外を書き換えて、ゲートそのものを弱められた**（修正済み）

    - **原因** ── 巻き戻し（`resetWork`）が戻すのは `src` と `tests` だけ、それ以外は書き換えたまま その走のあいだ効き続ける

        - `stryker.config.json` の `excludedMutations` に生き残る種類だけ足す（全部 除外すると「変異が1個も作られなかった」で捕まるが、部分的なら通る）→ 生き残り2で不合格だった実装が 生き残り 0/2 で合格 → main へ

29. **ワーカーは自分のタスクを `bd close` して、不合格を人から隠せた**（修正済み）

    - **見つけ方** ── ドキュメントの断定「ワーカーに commit / close の権限を渡さない」の close の側を確かめた
    - **実測** ── `bd close` は誰からでも通る（作業コピーから `BEADS_ACTOR` 無しで exit 0・`✓ Closed`）、閉じたタスクは `bd list --label blocked-for-human` に出てこない＝人に差し戻したはずの失敗が一覧から消える、他人のタスクを閉じればキューごと消せる
    - **偶然に頼っていた** ── ハーネス経由の実走では偶然 戻っていた（人に差し戻した直後に見ると open のまま）が、同じ順序を手で再現すると閉じたままだった、タイミング依存の偶然であって設計された防御ではない
    - **修正** ── 呼び出しの前後でタスクの一覧と状態を比べ、増えたタスクは閉じる／勝手に閉じられたタスクは開け直す（`restoreTasksChangedBy`）
    - **再検証**（$0） ── 「ワーカーが閉じたタスクを開け直した」の後、通常どおり生き残り2で不合格 → 人の一覧に差し戻しが残る
    - **教訓** ── 「保存させない」だけでは足りない、「失敗を人に届ける経路」も同じだけ守る、静かに消える失敗は通ってしまう失敗と同じくらい悪い

30. **「権限が無い」という言い方が、ドキュメント全体に散らばっていた**（修正済み）

    - **もう1つ食い違っていた** ── `チェック一式（ビルド＋テスト＋型）` も実装と違った、ハーネスが呼ぶのは `npm test` だけで `tsc`・lint・build の実行は実装に1箇所も無い

33. **ワーカーが作ったタスクを閉じる仕組みが、人が足したタスクも閉じていた**（修正済み）

### ゲートの迂回を再検証する（$0・[stub-worker-attack.mjs](stub-worker-attack.mjs)）

**動いた経過** ── claude が yaml を読む → テスト追加 → 赤先行 → **`src` を実修正**（`options.ts` と stringify の2ファイルに `eol` を実装）→ 全3386テストが緑 → **変更した行だけ** Stryker（変異8個＝ファイル全体を変異させる問題を回避できた）

**生き残りの正体** ── 毎回 `eol: '\n'`（**デフォルト値の `StringLiteral`**）、3回とも別の実装（非決定）だが同じ穴、**冗長なデフォルト値が生む等価変異らしい**（`validateUser` と同じパターンで、差し戻して人が判断する出口）

**コストが高い理由** ── おもちゃの題材（$0.6〜1.4）の5〜10倍、claude が毎回 本物のコードを読み直すうえ4ファイルにまたがり、3回とも最後まで走ったため

**答え（正直に）:**
1. **難所ゲートは 本物の複雑コード×実保守タスクでも正しく機能した**——弱いテスト（デフォルト値 未検証）を妥協せず人に差し戻し、**変更した行だけを変異させることで、ファイル全体の問題を実コードで回避できた**
2. **代償**：人への差し戻しが頻発（StringLiteral/等価変異が実コードで多い）＋**高コスト（$6.7/件）**＋遅い（30分）
3. **見つかったゲートの穴＝修正済み**：凍結がテストを書く段階で足したテストしか対象にしておらず、実装段階で"他の既存テスト"を弱めるズルを検出できなかった → **`tests/` 全体を凍結するよう修正**（[harness/integrated.mjs](../harness/integrated.mjs) の `frozen`）
4. ＝**実運用の残課題＝コスト最適化（呼び出し回数↓）**、StringLiteral 除外は"やらない"（本物シグナルを殺す）／凍結強化は済み
   これ以上（製品として配れる形にする）は別のリポジトリで扱う（重い並列ループ全部ではなく **難所ゲートの切り出し**）、この playbook は実証の記録として完了

tempo/tinyexec が Windows で緑にならなかった検証結果は 上の表に記録済み（clone 自体は使い捨てのため削除）

## ナレッジグラフの道具でコストが下がるか（検証して採用しなかった・2026-08-18）

**動機** ── 既知の限界の1つ「複雑なリポジトリほど重い＝AI が毎回コード全体を読む」を削れるか、本物のリポジトリを回した走は $6.74・6呼び出し・30分で、その理由は claude が毎回 本物コードを読み直すことだった（上の実測節）

**試したもの** ── [claude-cartography](https://github.com/shumatsumonobu/claude-cartography) が使う3つの道具

| 道具 | 何をするか | 対象 |
|---|---|---|
| Graphify | コードとドキュメントのナレッジグラフ、スキルとして呼ぶ | コード・文書・画像 |
| better-code-review-graph | コードのグラフと意味での検索、MCP で繋ぐ | コード |
| Serena | 言語サーバー（LSP）のインデックス、MCP で繋ぐ | コード |

**測り方**

1. **道具の実仕様を先に読む**（$0） ── ソースと `--help` で、呼び出しの形・引数・既定値を確かめる、ここを飛ばして使い分けを書くと**動かない呼び出しを指示することになる**
2. 実仕様どおりの使い分けを対象リポジトリの CLAUDE.md に書く
3. 同じプロンプトを道具の有り／無しで各3走、`claude -p --output-format stream-json` から読み込みトークン・時間・呼ばれた道具を取る
4. **道具が実際に呼ばれたかを見る** ── 呼ばれていなければ差が出るはずがない、使い分けの書き方を直して測り直す

リポジトリ外（`C:\dev`）で回す

### 結果

3つの題材すべてで、道具 有りが負けた

| 題材 | 道具 無し | 道具 有り |
|---|---|---|
| eemeli/yaml（22k行・タスク文からファイル名を外した条件） | 618,625tok / 196秒 | 629,413tok / 335秒 |
| prettier（166k行・探索が要るタスク） | 983,208tok / 301秒 | 1,325,693tok / 363秒 |
| withastro/docs（文書416本・コード無し） | 381,955tok / 139秒 | 926,687tok / 195秒 |

**精度でも寄与を確認できなかった** ── 「変更が必要な箇所を漏れなく挙げる」形でも聞いた

- prettier では道具 有りの方が広く挙げたが、**追加分はすべて `Grep` 由来**（ケバブケースで引き直した・`glob` を絞らなかった、という引き方の差）で、グラフの呼び出しが直接 見つけたものは無かった
- withastro/docs で唯一 価値のあった指摘（新しいガイドと矛盾する CSP の制約）を出したのは**道具 無しの走**、Graphify を入れた走はいずれも落とした

**導入のコスト** ── Graphify のグラフを1回 作るのにかかった分

| 対象 | 走全体の読み込み | 所要 | Graphify 自身が数えた抽出ぶん |
|---|---|---|---|
| eemeli/yaml（93ファイル） | 2,457,136トークン | 14分 | 入力 100,496 |
| prettier（560ファイル） | 2,517,099トークン | 18分 | 出力 170,255 |
| withastro/docs（416ファイル・全部 文書） | 12,115,877トークン | 2時間 | 入力 1,974,341 |

**この3つを1ファイルあたりで割って比べてはいけない** ── `cost.json` の計上の仕方が3つで違い（入力に出る・出力に出る）、走全体の読み込みには**ワーカーがグラフ構築とは別に探り回った分**が混ざる

言えるのは**規模が上がると桁で増える**ことと、**文書だけの題材が最も高い**ことまで（コードは構文解析で無料、文書は1本ずつ LLM が読む）

### 分かった理由

- **MCP の道具は遅延読み込み**で、最初の道具一覧に入らない、`ToolSearch` で取りに行く指示を書かないと存在しないのと同じになる
- **道具の使い分けの表は「質問」用に書かれている**、ループが渡すのはタスクなので、実装や修正のタスクを受けた時の手順を別に書かないと発火しない
- **`Grep` が既に十分に速い** ── prettier の166k行から手本にすべきオプションを3走とも一発で見つけ、読んだ成果物は2本だけだった、削る余地が無いところに往復の費用が乗る

### この検証の限界

- **書き直しが重なる走（ループ通し）は測っていない** ── 毎回まっさらな `claude -p` が同じ探索をやり直す部分は未検証で、そこだけ理屈が残る
- **Graphify のスキルと本体のバージョンがずれたまま測った**（skill 0.9.28 / package 0.9.44・警告が出続けていた）
- **各条件 3走** ── 幅が重なる差については断定していない

## まだ検証していないこと

**「動く」＝「設計の要件が全部できた」ではない**

**実装状況の一覧（何を作って、何がまだか）は [DESIGN.md §6](../DESIGN.md#6-実際にできるか正直に) の表を見ること**（そこが SoT）、ここに書くのは**検証が届いていない所**だけ

**難所（テストの信頼性）は部品ごとに決着している** ── 3つのゲート、書き直し・やり直し・人への差し戻し（`harness7.mjs`）、自己チェック（`selfcheck.mjs`・落とし穴12）、さらに土台とゲートと自己チェックを1本に統合して `claude` を実際に呼んで通した（`integrated.mjs`・上の実測節）

届いていないのは次の7つ

- **タスク文の書き方で読み込みが変わるか** ── eemeli/yaml で触るファイルを名指しした場合と外した場合を3走ずつ測ると 1,136,948トークン / 282秒 と 618,625トークン / 196秒 で幅が重ならず、結果（辿り着いた実装箇所）はどちらも同じだった、[sample/](../sample/) の題材（10ファイル規模）では未検証なのでタスク文の書き方は変えていない
- **統合の衝突を AI に解かせる** ── 今は `merge --abort` して人の対応待ち、綺麗に merge できる場合はスタブで実証済み（並列2枝・main 11テスト全緑）
- **自己チェックが人に差し戻すまでを、統合版で1回 踏む** ── 変異ツールが壊れた環境（CommonJS など）を仕込む必要がある、単体では実証済み
- **差し戻し率がどれだけ下がるか** ── 差し戻したタスクの自動投げ直しは機構として実証済み（スタブでの `MAX_ROUNDS` の動きと、`claude` を実際に呼んだ走での救済の両方）、率の効果は実ワークロード待ち
- **呼び出し回数の最適化** ── ナレッジグラフの道具は効かないと分かった（[上の節](#ナレッジグラフの道具でコストが下がるか検証して採用しなかった2026-08-18)）、他の手は未着手
- **人に差し戻した時の通知** ── いま差し戻しは `blocked-for-human` を付けて claim を解放するだけ、席を離れる（放置モード）なら通知が要る
- **本数を増やした時の速度の限界** ── 変異テストは1ファイル 3〜10秒（実 Express API 全体で 17秒）、統合版は既に変更した成果物だけを対象にしているが、ワーカーを増やした時の限界は未実測
