# loop-engineering-playbook

**AI にコードを書かせ続けるループを、人が毎回レビューしなくても信用できる形で1本 作って実証したもの ── 手元のプロジェクトにそのまま導入可能**

タスクの文章を1つ渡すと、AI が実装とテストを書き、自動の判定に合格したものだけをコミット

指示を出し直す作業を人が繰り返すのではなく、AI が自律的に働き続けられる仕組みそのものの設計 ── リポジトリ名の**ループエンジニアリング**はこの考え方のこと

このリポジトリに入っているもの

- **ハーネス** ── ループを実行するスクリプト（[harness/integrated.mjs](harness/integrated.mjs)）、`claude` を呼び出して合否を判定する側、手元のプロジェクトへ導入可能（[導入先の要件](#導入先の要件)あり）
- **ループを実行した題材3つ** ── そのまま複製して試せる一式（[sample/](sample/)）
- **検証の記録** ── 各段階で何を確かめたか・実測のコストと時間（[proof/](proof/)）

AI にコードを書かせると テストも AI が書く、だが AI は**実行は通るが何も検証していないテスト**を書くことがある（例 `expect(true).toBe(true)`）

行カバレッジ100%・全テストが通っていても、戻り値を一度も確認していないことがある

だから**テストの質そのものを採点するゲートを置く** ── 実装を機械的に1箇所ずつ壊し、テストが検出するかを確認（`return "zero"` を `return ""` に書き換えても全テストが通るなら、そこを検証しているテストは1本も無い）

これは**変異テスト**という手法、このループでは[3つのゲート](#3つのゲート)の③ **変異チェック**の役割

検出できない壊し方が1つでもあれば不合格、そのタスクはコミットされない

## 仕組み

以降、テストが全部通る状態を**緑**、1つでも落ちる状態を**赤**と呼ぶ

### 人と AI の役割

- ループの実行中、人が書くのは タスクの文章だけ、コードとテストは AI（`claude`）が書く ── この `claude` のプロセスを**ワーカー**と呼ぶ
- AI の自己申告は信用しない、テストの実行も 変異チェックも ハーネス自身が担当

タスクの管理には [beads](https://github.com/gastownhall/beads)（`bd`）というタスク管理ツールを使う、**操作ごとに担当は固定**

| 操作 | 誰が |
|---|---|
| タスクを登録する（`bd create`） | **人** |
| 担当を割り当てる（`bd update --claim`） | ハーネス |
| テストとコードを書く | ワーカー（成果物の置き場所（既定 `src/`）と `tests/` だけ） |
| 成果を保存する（`git commit`） | **ハーネスだけ** |
| タスクを完了にする（`bd close`） | **ハーネスだけ**（合格した後） |
| 差し戻されたタスクを見る（`bd list --label blocked-for-human`） | **人** |

ワーカーは複数を同時に実行可能

- ワーカーごとに別の作業コピー（git worktree）を持ち 互いのファイルを触らない
- 1つのタスクを担当するワーカーは1つだけ、同じタスクを複数が同時に進めることは起きない

### 1タスクの流れ

1タスクの進む順は下の図、順序を管理するのは AI ではなくハーネス（各ゲートの判定は[下の表](#3つのゲート)）

![1タスクの流れ: テストを書く、赤先行、凍結、実装を書く、全テスト緑、変異チェックの順に進み、不合格ならテストから書き直す。上限まで合格しなければ人に差し戻す](figures/loop-dark.png)

### 3つのゲート

順に判定し、1つでも不合格ならそのタスクはコミットされない

| ゲート | 判定 |
|---|---|
| **① 赤先行** | 実装が無い状態でテストを実行し、緑になってしまうなら不合格（何も検証していない）|
| **② 凍結** | 実装前の `tests/` 全部の内容を記録しておき、実装中に1文字でも書き換えられていたら不合格（テストを弱めて通す不正を防ぐ・今回のタスクと無関係な既存テストも対象）|
| **③ 変異チェック** | 実装を機械的に1箇所ずつ壊し、どれかの壊し方に全テストが緑のままなら不合格（JavaScript / TypeScript は Stryker、他の言語は[自分で書いたものに差し替え](#変異チェックの差し替え-成果物を壊すプログラムを自分で書く)）|

①と②はセットで機能、片方だけだと実装中にテストを弱めて通せてしまう

③で緑のままだった壊し方を**生き残り**と呼ぶ

補助が2つ

- **自己チェック**（Stryker を使う時だけ）── 変異ツール自体が実際のコードで誤動作して誤判定することがあるため、生き残りを通常のテスト実行で検算
- **人への差し戻し** ── 不合格が続いたタスクだけを人に差し戻し（既定は最大6回・環境変数 `MAX_ATTEMPTS` と `MAX_ROUNDS` で変えられる）、ループ全体は止まらない

### 規約違反への対処

役割を決めただけでは守れない ── ワーカーは自分の作業コピーの中で `git` も `bd` も動かせるし、実装ファイルには何でも書ける、だから呼び出しの前後でハーネスが検出・復元

| ワーカーがやること | ハーネスの対応 |
|---|---|
| 自分で commit する | 取り消す（中身は残してゲートで判定させる）|
| 自分でタスクを閉じる | 開け直す（閉じられると 差し戻した失敗が人の一覧から消える）|
| 成果物の置き場所と `tests/` の外を書き換える（設定・テストコマンド）| 元へ戻す（判定の材料を採点される側に触らせない）|
| 変異チェックを無効にする印（`// Stryker disable`）を書く | 不合格にする |

ゲート②が防ぐ「既存テストの改変」も含めて、どれも**実際に迂回できることを確かめてから防いだ**、再検証は [proof/stub-worker-attack.mjs](proof/stub-worker-attack.mjs) で実行可能（$0）

防ぐのは**規約違反**まで、**意図的に妨害する相手は対象外**（→ [既知の限界](#既知の限界)）

### 使用ツール

| ツール | 何のツールか | ここでの役割 |
|---|---|---|
| [Node.js](https://nodejs.org) | JavaScript の実行環境 | ハーネスの実行 |
| [Claude Code](https://code.claude.com/docs)（`claude -p`） | Anthropic 公式の AI コーディングエージェント | CLI で呼び出し、コードとテストを書く役（ワーカー） |
| [beads](https://github.com/gastownhall/beads)（`bd`） | AI エージェント向けのタスク管理ツール | タスクの登録と 担当の割り当て |
| [git worktree](https://git-scm.com/docs/git-worktree) | 1つのリポジトリから複数の作業コピーを作れる git 機能 | ワーカーごとの作業コピーを分離 |
| [Vitest](https://vitest.dev) | Vite ベースのテストフレームワーク | テストの実行と合否判定（**導入先が JavaScript の場合**、Python なら pytest など） |
| [Stryker](https://stryker-mutator.io) | 変異テストツール（JavaScript/TypeScript・C#・Scala に対応） | 実装を機械的に壊してテストの不足を発見（**それ以外の言語は自分で書いたものに差し替え**） |

## ユーザガイド

**何を作らせるかで「合格」の意味が変わる** ── 3つのゲートが見るのはテストの結果だけ、テストで検証できないことは合格に含まれない

| 作らせるもの | 合格の意味 | 例 |
|---|---|---|
| コード | テストが振る舞い（入力に対する出力）を検証できるので、**合格したら完成として扱える** | [sample/express-api/](sample/express-api/) |
| 記事・文書 | テストで検証できるのは形式（要素の有無・構造）だけ、**合格しても中身の正しさは自分で確認** | [sample/article-loop/](sample/article-loop/) |
| テストが書けないもの（リサーチ・作る/作らないの判定） | **対象外**、ゲートを外す設定は無い | なし |

対象外のものでも、テストが書ける部分だけをタスクに切り出す方法はある

向くのは**独立した小さいモジュールの追加**、既存の大きいファイルの改変は合格しにくい ── 変異チェックは変更したファイルの**全行**が対象のため、今回の修正と無関係な既存の未検証箇所まで生き残りとして報告

1タスクあたり **$0.41〜$6.74**、最も高いのは不合格だった実行（[コストと時間](#コストと時間)）

### 導入先の要件

**ソースコードの言語は問わない** ── ハーネスは導入先のリポジトリで `npm install` と `npm test` を実行するだけで、テストの中身は何でもよい（実行の記録は JavaScript が大半、TypeScript 2回、Python 1回）

言語で変わるのは**変異チェック（ゲート③）だけ** ── [Stryker](https://stryker-mutator.io) が JavaScript/TypeScript・C#・Scala 専用なので、それ以外の言語では自分で用意（下の[それ以外の言語の場合](#それ以外の言語の場合-変異チェックだけ自分で書く)）

#### 言語に関係なく必須

| 要件 | 外れている場合 |
|---|---|
| Node.js と、導入先の `package.json` に `scripts.test` | `scripts.test` が無いと `npm test` が失敗し続けて全タスクが人に差し戻し、中身は `vitest run` でも `python -m pytest -q` でもよい |
| テストが `tests/` にある | `tests/` は固定なので移動が要る（成果物の側は `WORK_ROOT` で変えられる・既定は `src/`） |
| 最初に全テストが緑 | 赤いテストがあると全ワーカーのゲートが不合格 |
| テスト一式が2分以内に終わる | ハーネスが `npm test` を120秒・変異チェックを900秒で打ち切って赤扱いにするため、超えると全タスクが差し戻し（[harness/integrated.mjs](harness/integrated.mjs) の `T` を変える＝ハーネスの改造） |

#### JavaScript / TypeScript の場合 ── Stryker をそのまま使える

| 追加の要件 | 外れている場合 |
|---|---|
| テストランナーが [Vitest](https://vitest.dev) | [Jest](https://jestjs.io) でも動作（実測 $0.81・変異9個中 生き残り0）、設定の差し替えと環境変数が要る（下の[Jest の場合](#jest-の場合-設定の差し替えと環境変数)） |
| ESM（`package.json` に `"type": "module"`）| CommonJS なら `import` / `export` へ書き換え（下の[セットアップ](#セットアップ)で）、そのままだと Stryker が変異を適用できず 生き残りを誤検出（実測は [proof/README.md](proof/README.md)） |

**TypeScript は改造なしで動作**（実測 $0.90・変異13個中 生き残り0）── 型チェックはゲートに含まれない（[既知の限界](#既知の限界)）

#### それ以外の言語の場合 ── 変異チェックだけ自分で書く

**ESM も Vitest も要らない**（どちらも Stryker のための要件）、ハーネスの改造も要らない

成果物を壊すプログラムを1本 書いて差し替え（書き方は下の[変異チェックの差し替え](#変異チェックの差し替え-成果物を壊すプログラムを自分で書く)）

自作した場合、壊し方の網羅性は自分で書いた分だけ → [既知の限界](#既知の限界)

### セットアップ

**この手順は JavaScript / TypeScript・テストランナーが Vitest のプロジェクト向け**

構成が違うなら、**手順に入る前に**下の2節を確認 ── どちらも手順の中でやることが変わる

- テストランナーが Jest → [Jest の場合](#jest-の場合-設定の差し替えと環境変数)（依存とテストコマンドの設定が変わる）
- JavaScript 以外の言語・コード以外の成果物 → [変異チェックの差し替え](#変異チェックの差し替え-成果物を壊すプログラムを自分で書く)（どこがどう変わるかの対応表と一式は [sample/python-pytest/](sample/python-pytest/)）

前提は Node.js 20 以上・git・[Claude Code](https://code.claude.com/docs)（beads は下の手順でインストール）── Node 20 以上は 下でインストールする Vitest と Stryker の要求、検証は Node 24 で実施

ここでの**プロジェクト**は ループを実行したいリポジトリ、**ハーネス**は clone した `loop-engineering-playbook`

コマンドの実行場所は 各手順に書いたルート

**プロジェクト側で用意・変更するもの**（ハーネスは書き換えない）

**JS/TS 専用** の印が付いた行は、構成によって別のことをする（[Jest の場合](#jest-の場合-設定の差し替えと環境変数)／[変異チェックの差し替え](#変異チェックの差し替え-成果物を壊すプログラムを自分で書く)）

| 対象 | すること | 手順 |
|---|---|---|
| `package.json` | `"test"` にテストコマンドを書く、**JS/TS 専用** ── `"type": "module"` と 開発依存の Vitest・Stryker | 3・5・6 |
| 既存のコード | **JS/TS 専用** ── CommonJS なら `import` / `export` へ書き換え | 5 |
| 成果物の置き場所 | `src/` に置く（別の場所なら環境変数 `WORK_ROOT` で指定） | 4 |
| テストの置き場所 | `tests/` に置く（固定・別の場所にあるなら移動） | 4 |
| `stryker.config.json` | **JS/TS 専用** ── ハーネスからコピーして直下へ（他の言語では代わりに 成果物を壊すプログラムを1本 書く） | 7 |
| `CLAUDE.md` | コーディング規約を追記 | 8 |
| `.gitignore` | ツールが作る未追跡ファイルを除外 | 10 |

1. **beads をインストール**（グローバルにインストールされるので1回だけ）

   ```bash
   npm install -g @beads/bd@1.1.0   # 検証済みの版、Homebrew なら brew install beads
   ```

2. **ハーネスを取得**（置き場所は任意）

   ```bash
   git clone https://github.com/shumatsumonobu/loop-engineering-playbook
   ```

3. **プロジェクトのルートで 依存を追加して beads を初期化**

   ```bash
   cd /path/to/my-repo   # ループを実行したいプロジェクトのルート
   npm install -D vitest@4.1.10 @stryker-mutator/core@9.6.1 @stryker-mutator/vitest-runner@9.6.1   # 検証済みの版
   bd init
   ```

   `bd init` は `.beads/`・`AGENTS.md`・`.agents/`・`.codex/`・`CLAUDE.md`・`.gitignore`・`.claude/settings.json` を作成して自分でコミット（**既にあるファイルは消さずに追記**）

4. **プロジェクトの成果物とテストの置き場所を合わせる**

   成果物は `src/`・テストは `tests/` に配置、ハーネスが見るのはこの2つだけ

   成果物の置き場所を変えたい場合は 環境変数 `WORK_ROOT` にディレクトリ名を指定（既定 `src`・例 `WORK_ROOT=app`）

   テストは `tests/` 固定、既存のテストが `test/` や `__tests__/` にあるなら `tests/` へ移動

   ファイル名は自由（**JS/TS 専用** ── Vitest は `*.test.js` も `*.spec.js` も対象にするので改名は要らない）

5. **プロジェクトを ESM に設定**

   package.json に `"type": "module"` を追加

   既存コードが CommonJS（`require` / `module.exports`）なら **`import` / `export` へ書き換え**、`"type": "module"` を足しただけでは動かない

   書き換えるのは**リポジトリ全体**、ハーネスが触らないファイル（ビルドスクリプトなど）も `"type": "module"` の影響を受けて `require` が動かなくなる

   TypeScript なら `tsconfig.json` も調整 ── `"module"` と `"moduleResolution"` を `nodenext` にして、相対 import に `.js` 拡張子を付与（`from "./money.js"`）

   `"type": "module"` を足しただけだと `tsc` が出力するコードは CommonJS のままで実行できなくなる、**`tsc --noEmit` は緑のままなので気づけない**

6. **プロジェクトのテストコマンドを設定**

   package.json の scripts に `"test": "vitest run"` を追加

   TypeScript で型もゲートに含めたいなら `"test": "tsc --noEmit && vitest run"` に変更（ゲートが見るのは `npm test` の結果だけ）

   テストが1本も無い場合は、既にある関数を1つ選んで `tests/` にテストを1本作成（vitest はテスト0本だと失敗する）、コード以外が成果物なら 既にある成果物を1つ検証するテストを1本

   確認: `npm test` で全テストが緑

7. **Stryker の設定をプロジェクトへコピー**

   [harness/stryker.config.json](harness/stryker.config.json) をプロジェクトの直下へ配置

   設定の `mutate` は書き換えなくてよい ── 変異の対象はハーネスが実行時に「そのタスクで変更したファイル」を指定（`mutate` が効くのは手で `npx stryker run` を実行する時）

8. **プロジェクトの CLAUDE.md にコーディング規約を追加**

   書くのはプロジェクト固有の規約だけ（ループの動作指示はハーネスがプロンプトで渡すので要らない）

   推奨は次の2つ、どちらも 変異チェックが不合格を出しやすい書き方の予防

   ```markdown
   ## コーディング規約
   - エラーを検証するテストは 文言の全文を固定しない、文言の一部だけを部分一致で検証する（例 `toThrow(/min/)`）
   - テストが要求していない分岐や 念のためのガードを実装に書かない
   ```

   `bd init` が追記した `## Session Completion` の項目「**File issues for remaining work**」は削除 ── タスクを決めるのは人なので、ワーカーが作業の終わりに issue を立てる必要は無い（消し忘れてもハーネスが検出して閉じる）

   実際に使った例は [sample/express-api/CLAUDE.md](sample/express-api/CLAUDE.md)

9. **プロジェクトのルートで タスクを登録**

   ```bash
   bd create "URLスラッグへの変換を実装" -d "src/slugify.js に 文字列をURLスラッグへ変換する slugify(s) を実装し、tests/slugify.test.js で 空文字・記号・連続スペースまで検証する"
   ```

   `-d`（説明）に書いた文章がそのまま AI への仕様、「どのファイルに・何を・どうテストするか」まで記述

   題名は 500バイト（日本語なら約160文字）までしか入らない、ハーネスがワーカーへ渡すのは題名と説明の両方

10. **プロジェクトの未コミットの変更を無くす**

    ハーネスは 今のコミット状態から作業コピーを作るため、未コミットの変更は反映されない

    `npm install` で作られた `package-lock.json` はコミット、使っているツールが自動で作ったファイル（`.serena/` など）が未追跡で残っていたら `.gitignore` へ追加

    確認: `git status` に変更が残っていない ── 残したまま次へ進むと**警告も出ずに古い状態のまま実行される**

### Jest の場合 ── 設定の差し替えと環境変数

テストランナーが [Jest](https://jestjs.io) でも動作、Vitest との違いは2つ

- `stryker.config.json` の `"testRunner"` を `"jest"` にして `@stryker-mutator/jest-runner` を開発依存に追加
- **ESM の Jest には `NODE_OPTIONS=--experimental-vm-modules` が要る** ── `npm test` 側だけでなく**ハーネスを起動する時にも渡す**（Stryker は自分で Jest を起動するため、無いと変異チェックが初回実行で失敗する）

```bash
NODE_OPTIONS=--experimental-vm-modules BASE=/path/to/my-repo node harness/integrated.mjs
```

### 変異チェックの差し替え ── 成果物を壊すプログラムを自分で書く

Stryker が使えない言語（Python など）と、コード以外の成果物（markdown の記事など）では、成果物を壊すプログラムを自分で書いて `MUTATOR` で差し替え

やることは3つ

1. **`package.json` を1つ置く** ── 中身は `{"scripts": {"test": "<自分のテストコマンド>"}}` だけでよい（例 `python -m pytest -q`）
2. **成果物を壊すプログラムを `.mjs` で1本 書く**（以下 **変異器**・書き方は下）── 実例 [mutate-py.mjs](sample/python-pytest/mutate-py.mjs)（Python）／[mutate-md.mjs](sample/article-loop/mutate-md.mjs)（markdown）
3. **`MUTATOR` を付けて起動する** ── `MUTATOR=/path/to/mutate-py.mjs BASE=/path/to/my-repo node harness/integrated.mjs`、指定すると Stryker は呼ばれない

**変異器の書き方** ── 関数を1つ `export default` し、返す値は次の3つ

```js
export default async function mutate(w, files, { runTest }) {
  // w.dir   … ワーカーの作業コピーの絶対パス
  // files   … 変異させる成果物のパス（リポジトリからの相対）
  // runTest … テストを1回 走らせる、{ code } が返る（0 以外＝赤＝その壊し方を検出できた）
  return {
    total: 0,        // 作った壊し方の数（0 だと「チェックが効いていない」として人に差し戻される）
    output: "",      // 判定に使った出力（不合格の時に記録として残る）
    survivors: [],   // 緑のままだった壊し方
    //   1件の形: { file, original, mutant: { mutatorName, location: { start: { line } }, replacement } }
    //   これがそのまま書き直しの指示になる（「◯◯:12 の A を B に書き換えても緑のままでした」）
  };
}
```

中身は**壊す → `runTest()` → 元へ戻す**の繰り返しだけ（[mutate-py.mjs](sample/python-pytest/mutate-py.mjs) がそのままの形）

自作にすると[自己チェック](#3つのゲート)（Stryker の生き残りを素のテスト実行で検算する補助）は動かない ── 自分で壊して自分でテストを走らせるので、ツール側が壊れている疑いが無いため

一式は [sample/python-pytest/](sample/python-pytest/) ── Python + pytest で**1回目に合格**（実測 $0.58・変異16個中 生き残り0・158秒）

### 使い方

#### 実行する

ハーネスのルートで、プロジェクトのパスを環境変数 `BASE` に指定

```bash
cd /path/to/loop-engineering-playbook                 # clone したハーネスのルート
BASE=/path/to/my-repo node harness/integrated.mjs     # ワーカー1つ
BASE=/path/to/my-repo node harness/integrated.mjs 2   # 並列2つ（最大4）
```

- Windows は Git Bash で実行、パスは `/c/path/to/my-repo` の形式で渡す（PowerShell なら `$env:BASE="C:/path/to/my-repo"; node harness/integrated.mjs`）、macOS / Linux は `/path/to/my-repo` のような通常のパス
- 実行すると最初に `対象: <解決後のパス>｜成果物: <置き場所>｜変異チェック: <種類>` が出る、**ここが意図した場所でなければ止めて `BASE` を渡し直す**（対象が git リポジトリでなければ ハーネスは何もせず終了する）
- 以降は全自動、`claude` の呼び出しごとに課金、タスクが無くなるとワーカーは自動終了
- プロジェクトの隣に作業コピー `<プロジェクト名>-w1`（並列なら `-w2` …）を作成、作業コピーごとに ハーネスが npm install を実行するためディスクを 各 約96MB 使用

#### 結果を確認する

プロジェクトのルートで

```bash
cd /path/to/my-repo                  # プロジェクトのルート
bd list --label blocked-for-human    # 人に戻ってきたタスクの一覧
```

| 結果 | ハーネスの動作 | 人がすること |
|---|---|---|
| 合格 | ワーカーのブランチに commit、元のブランチへ統合して全テストを再実行し 緑なら採用、タスクを完了 | なし |
| 不合格 | `blocked-for-human` ラベルを付けてタスクを人に差し戻し | 原因を直してから再実行 |
| 統合できなかった（結果表示が「衝突して中止」＝他の変更と競合、「赤なので巻き戻した」＝統合後にテストが失敗） | 成果はワーカーのブランチ（`w1` など）に残り、元のブランチには入らない、タスクは閉じられている | この表示を見て判断 |

不合格の中身は 作業コピーと同じ場所の `<プロジェクト名>-log/run-<実行日時>/` に1件1ファイルで保存、落ちたテストの出力・生き残った変異・巻き戻す前のコードとテストを確認可能（実行するたび別の場所に作られるので前回の記録は消えない）

不合格の主因は 実装の冗長さ（どのテストでも検出できない変異を生む）か テストでは検証できない仕様

#### 後片付け

プロジェクトのルートで 作業コピーを削除

```bash
git worktree remove --force ../<プロジェクト名>-w1
# 並列で実行したなら -w2 以降も同じように削除
```

実行中に生まれた未追跡ファイルがあるため `--force` が必要

不合格の記録（`../<プロジェクト名>-log/`）も不要なら削除してよい

#### 設定一覧

ハーネスを変更せず、環境変数で変更可能 ── 指定しなければ既定値で動作

| 環境変数 | 既定 | 何が変わるか |
|---|---|---|
| `BASE` | `../sandbox`（**実質 必須**） | 対象のプロジェクトのパス ── 渡さないとハーネスの隣の `../sandbox` を探し、git リポジトリでなければ何もせず終了する |
| `WORK_ROOT` | `src` | 成果物の置き場所（テストは `tests/` 固定） |
| `MUTATOR` | 未設定（Stryker を使う） | 変異チェックを自分で書いたものに差し替え、書き方は[変異チェックの差し替え](#変異チェックの差し替え-成果物を壊すプログラムを自分で書く) |
| `MAX_ATTEMPTS` | `3` | 1つのタスクを書き直させる上限 |
| `MAX_ROUNDS` | `2` | 書き直しの上限に達した後、最初からやり直す回数 |
| `LOG_DIR` | `<プロジェクトのパス>-log` | 不合格の中身を残す場所 |

```bash
# 成果物の置き場所が src/ 以外・変異チェックが自作の場合
WORK_ROOT=lib MUTATOR=/path/to/mutate-py.mjs BASE=/path/to/my-repo node harness/integrated.mjs
```

### コストと時間

導入するか決める材料は [proof/README.md](proof/README.md)

**コストは題材で16倍の差**、合格した実行だけ見ると安く見えるので 不合格の実行も掲載

| 題材 | コスト | 時間 | 結果 |
|---|---|---|---|
| 独立した小さいモジュールの追加（10回） | $0.41〜$1.43 | 2〜7分 | 全部 合格 |
| 同一のタスク文を5回（`sample/express-api` と同じ仕様） | 計 $11.0（1回 $0.88〜$3.16） | 1回 7〜19分 | **4回は人に差し戻し・5回目だけ合格** |
| 本物のリポジトリの保守タスク（4ファイル跨ぎ） | **$6.74**（`claude` 6回） | **30分** | **人に差し戻し（合格せず）** |

そのほか

- `claude` を1回 呼ぶだけで**固定費 約$0.27**（毎回 文脈を約27kトークン読み込むため）、書き直し1回ごとに +約$0.54
- **高いのは不合格の時** ── 合格しない題材は書き直しのたびに不合格を繰り返すので、差し戻しを人が確認する運用が要る

### 検証の範囲

ゲート1つずつ → 統合 → 本物の OSS リポジトリ の順で検証、記録とコードは [proof/](proof/)

| 対象 | 方法 | 結果 |
|---|---|---|
| 各ゲート（赤先行・凍結・変異チェック・自己チェック・差し戻し） | 段階ごとに1本ずつ書いた検証スクリプト | 各ゲートの動作を確認 |
| ループを実行する部分（並列実行・作業コピーの隔離・担当の割り当て・統合） | 部分ごとに検証したあと、統合版 integrated.mjs を `claude` で実際に実行 | 統合版で最初から最後まで動作 |
| 本物の OSS リポジトリ `eemeli/yaml`（テスト3386本） | 保守タスクを実行 | ゲートが弱いテストを不合格 |
| **ゲートを迂回しようとするワーカー**（自分でコミット・変異チェックを無効にする印・既存テストの改変・変異ルールの除外・テストコマンドの差し替え・タスクを閉じて失敗を隠す） | **スタブ**（`claude` の代わりに置く、決まった動きをする偽のワーカー・課金されない）で再現（[proof/stub-worker-attack.mjs](proof/stub-worker-attack.mjs)） | **どれも防げることを確認** |
| 上のセットアップ手順 | README だけを情報源にした別の `claude` に繰り返し実行させる | 要件を3つとも外したプロジェクト（CommonJS・テストランナーが `node:test`・コードが `app/` でテストが `spec/`）でも、TypeScript のプロジェクトでも、ハーネスを書き換えずに 環境構築から merge まで完了 |
| 既存のブログのリポジトリ | 導入して記事1本を実行（[sample/article-loop/](sample/article-loop/) の実行とは別） | 3つのゲートに1回目で合格して統合まで到達（実測 $0.77・4.1分・変異10個中 生き残り0） |
| テストランナーが Jest のプロジェクト | 導入して実行 | 変異が1個生き残って書き直し、2回目で生き残り0 → 統合まで到達（実測 $0.81・4.2分） |

各段階の実測（コスト・所要時間・何が不合格になったか）は [proof/README.md](proof/README.md)

### 既知の限界

| 限界 | 理由と対処 |
|---|---|
| 複雑なリポジトリほど遅い（1タスク2分〜30分） | AI が毎回コード全体を読むため、ナレッジグラフの道具で減らせるか試したが効果なし（[proof/README.md](proof/README.md)） |
| 実コードでは人への差し戻しが多い | どのテストでも検出できない変異（等価変異）と、文言を固定しすぎたテストが出やすい |
| OS 依存のコードでは実行できないことがある | 最初に全テストが緑である必要があり、日付やプロセスのテストは環境差で緑にならない |
| コード以外の成果物は形式しか保証しない | 合格した記事の事実を嘘に書き換えても検証は通る、内容の正しさは人が確認（[sample/article-loop/](sample/article-loop/)） |
| 生き残り0 だと成果物が検証した要素だけに限られる | 記事では要点の列挙だけになる、検証項目の設計で調整 |
| 型チェックと lint はゲートに含まれない | ゲートが見るのは `npm test` の結果だけ、必要なら `"test"` に追加 |
| 「生き残り0」の意味は変異器で変わる | 自作の変異器は自分で書いた壊し方だけ（[mutate-py.mjs](sample/python-pytest/mutate-py.mjs) は行単位の正規表現で、構文木は解析しない） |
| 意図的に妨害する相手は止められない | ワーカーは権限の確認なしで動き、作業コピーの外にもファイルを書ける（防いでいない）、信用できないコードやタスク文には使わない |
| ハーネスは最小構成 | 常用するなら同じ判定を自分の自動化や CI に組み込み（設計は [DESIGN.md](DESIGN.md)） |
